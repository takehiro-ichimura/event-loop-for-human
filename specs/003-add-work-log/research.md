# Research: 作業ログ機能

**Feature**: 003-add-work-log | **Date**: 2026-02-14

## 1. LocalStorageキー戦略

**決定**: 単一キー `eventloop4human:logs` に配列として保存

**根拠**:
- 各ログエントリは約150-200バイト。5000件で最大1MB程度で、5MB制限の20%以下
- 分析やフィルタリングで全データを読む必要があるため、単一キーの方がparse回数が1回で済む
- 日付別に分割すると全期間の分析時に複数回のparseが必要で、むしろオーバーヘッドが増加

**検討した代替案**:
- 日付別の複数キー: 個別日のデータ取得は高速だが、全期間分析時に複数回readが必要で複雑化
- IndexedDB: 非同期API・インデックス機能があるが、プロジェクト要件がLocalStorageを指定

## 2. ログ記録アーキテクチャ

**決定**: (b) dispatchのラッパー関数パターン + 専用カスタムフック

**根拠**:
- Reducerは純粋関数であるべきで、副作用（ログ記録）を含めるべきではない
- `useEffect` で状態変更を監視する方式は、「何が変わったか」を検知するのが困難（前後の状態diff が必要）
- App.tsxのハンドラ（`handleAddTask`, `completeTask` 等）が明確な操作ポイント。これらをラップしてログを記録する`useWorkLog`フックが最適
- 各ハンドラは操作種別（作成・完了・ブロック・移動等）とコンテキスト（タスク名・from/to エリア）を明示的に知っている

**実装方針**:
```
App.tsx の各ハンドラ → useWorkLog.recordLog(操作情報) → LocalStorage保存
```

**検討した代替案**:
- (a) Reducer内部: 副作用の問題で不適切
- (c) useEffectで状態監視: 「何の操作が起きたか」を状態diffから推測する必要があり、不正確になるリスク
- (d) App内useEffect: 機能的には可能だが、ログロジックをApp.tsxに直書きすると関心の分離が不十分

## 3. CSV/JSONエクスポート

**決定**: Blob + URL.createObjectURL + 即時クリーンアップパターン

**根拠**:
- サーバー不要、クライアントサイドで完結する標準的なパターン
- 全モダンブラウザで対応済み
- `URL.revokeObjectURL()` で明示的にメモリ解放が可能

**実装上の注意**:
- CSVのBOMヘッダー（`\uFEFF`）追加でExcelでの日本語文字化け防止
- MIMEタイプ: `text/csv;charset=utf-8` / `application/json;charset=utf-8`
- DOM要素（anchor）の追加→クリック→削除→URL解放の順序遵守

## 4. ログリストの表示方法

**決定**: 「もっと見る」パターン（初期50件 + 50件ずつ追加読込）

**根拠**:
- プロジェクト憲章で「追加ライブラリ不要」「UIの複雑さを増やさない」と規定
- 仮想スクロールはライブラリなしでの実装が複雑（高さ計算、スクロール位置管理）
- 初期50件表示なら数ms以内でレンダリング可能
- 日付フィルタ適用後は件数が大幅に減るため、全件表示は稀

**検討した代替案**:
- 仮想スクロール（react-window等）: 最適だがライブラリ追加が必要で方針に反する
- 自作仮想スクロール: 実装・保守コストが高い
- 従来のページネーション: UX的に劣る（100ページ分のナビゲーション）
- 無限スクロール: Intersection Observerで可能だが、明示的な「もっと見る」ボタンの方がユーザーコントロールが明確

## 5. 日付フィルタリング

**決定**: ネイティブHTML `<input type="date">` + プリセットボタン

**根拠**:
- `<input type="date">` はHTML標準で全モダンブラウザ対応
- ライブラリ追加不要
- CSSでターミナル美学に合わせたカスタマイズが可能（背景色・フォント・ボーダー色）

**実装方針**:
- 開始日・終了日の2つの `<input type="date">`
- プリセットボタン: 「今日」「過去7日」「過去30日」
- クリアボタンで全期間表示に戻す

**制限事項**:
- カレンダーポップアップ部分のスタイリングはブラウザ依存（完全なカスタマイズは困難）
- ターミナルテーマとの統一感は入力フィールド部分で確保

## 6. ログ記録のタイミングと操作種別

**決定**: 以下の操作種別でログを記録する

| 操作種別 | トリガー | 記録データ |
|---------|---------|-----------|
| `created` | ADD_TASK dispatch | タスク名, 投入先エリア |
| `moved` | AUTO_DISPATCH / MOVE_TASK | タスク名, from → to エリア |
| `completed` | COMPLETE_TASK dispatch | タスク名, 経過時間（TimerStateから取得） |
| `blocked` | BLOCK_TASK dispatch | タスク名, callStack → webAPI |
| `paused` | timer.pause() | タスク名, 一時停止時の経過時間 |
| `resumed` | timer.resume() | タスク名, 再開時点の累積一時停止時間 |

**根拠**:
- spec.md のFR-001で定義された6種類の操作を網羅
- 各操作のハンドラが既にApp.tsxに存在するため、フック統合が容易
- TimerStateから経過時間を取得することで、完了時の正確な作業時間を記録可能
