# Feature Specification: 作業ログ機能

**Feature Branch**: `003-add-work-log`
**Created**: 2026-02-13
**Status**: Draft
**Input**: User description: "作業のログを残せるようにしたい。どんな作業をしたのか後から分析できるようにしたい。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 作業履歴の自動記録 (Priority: P1)

ユーザーがタスクを操作（作成・移動・完了・ブロック）するたびに、システムが自動的にログエントリを記録する。ユーザーは意識せずに作業履歴が蓄積されていく。

**Why this priority**: ログ機能の基盤であり、これがなければ分析も振り返りもできない。ユーザーの操作を邪魔せずバックグラウンドで記録することが最も重要。

**Independent Test**: タスクを作成→Microtask Queueに移動→Call Stackに配置→完了の一連の操作を行い、各ステップのログエントリが記録されていることを確認する。

**Acceptance Scenarios**:

1. **Given** ユーザーが新しいタスクを追加した、**When** タスクがTask Queueに追加される、**Then** 「タスク作成」のログエントリが記録される
2. **Given** Call StackのタスクをWeb APIにブロックした、**When** タスクがWeb APIエリアに移動する、**Then** 「タスクブロック（Call Stack → Web API）」のログエントリが記録される
3. **Given** タスクを完了した、**When** タスクがCall Stackから除去される、**Then** 「タスク完了」のログエントリが記録され、作成から完了までの経過時間が含まれる

---

### User Story 2 - 作業ログの閲覧 (Priority: P2)

ユーザーが過去の作業ログを時系列で一覧表示し、どんな作業をしたのかを振り返ることができる。

**Why this priority**: 記録されたログをユーザーが実際に確認できなければ価値がない。シンプルな一覧表示で過去の作業内容を把握できるようにする。

**Independent Test**: 複数のタスク操作を行った後、作業ログ画面を開き、すべてのログエントリが時系列順に表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 複数の作業ログが記録されている、**When** ユーザーが作業ログ画面を開く、**Then** ログエントリが新しい順に一覧表示される
2. **Given** 作業ログ画面が表示されている、**When** ユーザーが特定の日付でフィルタする、**Then** その日のログエントリのみが表示される
3. **Given** ログエントリが表示されている、**When** 各エントリを確認する、**Then** タスク名、操作内容、タイムスタンプ、移動元→移動先（該当する場合）が表示される

---

### User Story 3 - 作業パターンの分析 (Priority: P3)

ユーザーが蓄積された作業ログから、自分の作業パターンを分析できる。完了タスク数、タスクの平均所要時間、よくブロックされるタスクの傾向などを把握できる。

**Why this priority**: ログの真の価値は分析にある。ただし、US1・US2が先に成立している必要がある。まずはシンプルなサマリー統計から始める。

**Independent Test**: 1週間分の作業ログが蓄積された状態で分析画面を開き、完了タスク数・平均所要時間・日別の作業量が表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 過去の作業ログが蓄積されている、**When** ユーザーが分析画面を開く、**Then** 指定期間の完了タスク数、平均所要時間が表示される
2. **Given** 分析画面が表示されている、**When** ユーザーが期間を選択する、**Then** 選択した期間のサマリーが更新される
3. **Given** 十分なログデータがある、**When** 日別の作業量を確認する、**Then** 日ごとの完了タスク数が表示され、作業パターンの傾向が読み取れる

---

### Edge Cases

- 作業ログのデータ量が大量に蓄積された場合（数千件以上）でも、ログ一覧の表示がスムーズであること
- ブラウザのストレージ容量が逼迫した場合、古いログから自動的に削除する仕組みがあること
- タスクを作成して即座に削除した場合でも、作成ログは残ること
- 同一タスクが複数回ブロック→復帰を繰り返した場合、すべての移動が記録されること

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、タスクの各操作（作成、移動、完了、ブロック、一時停止、再開）ごとにログエントリを自動的に記録しなければならない
- **FR-002**: 各ログエントリは、タスク名、操作の種類、タイムスタンプ、移動元エリア、移動先エリアを含まなければならない
- **FR-003**: 完了したタスクのログエントリは、タスクの作成から完了までの経過時間を含まなければならない
- **FR-004**: ユーザーは作業ログを時系列順（新しい順）で一覧表示できなければならない
- **FR-005**: ユーザーは作業ログを日付でフィルタリングできなければならない
- **FR-006**: 作業ログは永続的に保存され、ブラウザを閉じても保持されなければならない
- **FR-007**: ストレージ容量が上限に近づいた場合、システムは古いログエントリから自動的に削除しなければならない
- **FR-008**: ユーザーは指定期間の完了タスク数と平均所要時間を確認できなければならない
- **FR-009**: ユーザーは日別の作業量（完了タスク数）を確認できなければならない
- **FR-010**: 作業ログの記録は、ユーザーの通常のタスク操作を遅延させてはならない

### Key Entities

- **ログエントリ (Log Entry)**: 1回のタスク操作を記録する。タスクID、タスク名、操作種別（作成・移動・完了・ブロック・一時停止・再開）、タイムスタンプ、移動元エリア、移動先エリア、経過時間（完了時のみ）を持つ
- **作業サマリー (Work Summary)**: 指定期間のログエントリを集計したもの。完了タスク数、平均所要時間、日別内訳を持つ

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーがタスクを操作した際、ログの記録処理が100ms以内に完了し、操作の体感速度に影響を与えない
- **SC-002**: 1000件のログエントリが蓄積された状態で、ログ一覧の表示が2秒以内に完了する
- **SC-003**: ユーザーが過去1週間の作業を振り返る際、日付フィルタ操作から結果表示まで1秒以内に完了する
- **SC-004**: 分析画面で表示されるサマリー（完了数、平均所要時間）が、実際のログデータと100%一致する

## Clarifications

### Session 2026-02-13

- Q: タイマーのポーズ（一時停止）/再開操作はログに記録するか？ → A: ポーズ/再開を個別のログエントリとして記録する（操作種別に「一時停止」「再開」を追加）
- Q: 作業ログ画面へのアクセス方法は？ → A: サイドバーにタブを追加し、タスク追加フォームとログ画面を切り替える方式とする

## Assumptions

- 作業ログの保存先は、既存のタスクデータと同様にブラウザのLocalStorageを使用する（既存の永続化インフラを拡張）
- ストレージの自動クリーンアップ閾値は、全体の80%使用時に古いログから削除を開始する
- 分析機能はリアルタイム集計とし、事前集計やバッチ処理は行わない
- 作業ログ画面・分析画面はサイドバー内にタブ切り替えで組み込む（既存のタスク追加フォームと並列のタブとして配置）
- ログの最大保持件数は5000件とし、それを超えた場合は古い順に削除する
